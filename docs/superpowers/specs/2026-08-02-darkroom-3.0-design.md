# PhotoEditor 3.0 — "The Darkroom"

A release in five phases: prove the features that exist, replace the film
conversion with a print engine, build the scanning workflow around it, make
the library usable at the scale of a shoebox of negatives, and publish.

Target: version 3.0.0. Major, because the conversion engine changes and the
catalog gains a schema migration.

This document is the roadmap. Each phase gets its own spec and its own
implementation plan when it is reached, so that a plan is written against the
code as it actually is rather than as it was forecast to be.

## Phase 1 — Prove the features that exist  ✅

### The problem

The suite is at 342 passing tests and there is not a single `TODO` in the
source, but neither fact establishes that a control is wired to anything.
Process Version 1 shipped a Highlights slider whose positive side was a silent
no-op, because `CIHighlightShadowAdjust`'s highlight side does nothing — and
every test passed the whole time. Tests asserted the *code* behaved as
written; nobody asserted the *image changed*.

### What gets built

**`ControlConformanceTests`** — a data-driven suite over a declared inventory
of every scalar control in `EditStack`. For each control, against a fixed
probe image with real shadows, midtones, highlights and saturated colour:

1. **Neutral is a no-op.** Rendering with the control at its neutral value
   produces a bit-exact match to rendering with a default stack. This catches
   a control that is quietly always-on.
2. **Both extremes move the image.** Minimum and maximum each produce a mean
   absolute difference above a floor well outside numerical noise. This is the
   test that would have caught PV1 Highlights.
3. **The direction is the declared one.** Each control declares what it should
   do to a measured statistic — mean luma, a percentile, saturation, local
   contrast — and the test asserts the sign of the change. This catches an
   inverted binding.

The inventory is a single table in the test file. A new control added to
`EditStack` without a row fails a completeness test that reflects over the
type's coding keys, so the matrix cannot silently rot.

**`CommandConformanceTests`** — every menu item and keyboard shortcut in
`EditorCommands` and `CullingCommands` resolves to a live action, and every
tool shortcut in `ToolKeyMonitor` activates the tool it advertises.

**Remediation.** Whatever the two suites expose gets fixed in this phase.

### Also in scope

- Delete the empty `Sources/Shaders/` directory (the `.ci.metal` files live
  in `Sources/Pipeline/Kernels/`).
- Un-gate the RAW fixture tests using the user's own files.

### Out of scope

Rewriting existing tests. This phase adds a layer that asserts a different
kind of property; it does not touch what is already there.

## Phase 2 — The print engine

Superseded in full by
[2026-08-04-print-engine-design.md](2026-08-04-print-engine-design.md).

The density model sketched here was right about the inversion and silent about
the rendering. A density inversion produces a scene-linear positive, which is
flat — it needs a paper response with a toe, a shoulder and a hue-preserving
highlight rolloff before it looks like a photograph rather than like data. The
Phase 2 spec covers both halves, plus the Auto solve.

## Phase 3 — The scanning workflow

Built for DSLR scanning on a copy stand, which is how these negatives are
actually digitised.

### Rolls

A film frame's real metadata is not in its EXIF. The EXIF describes the camera
that photographed the negative, not the camera that shot it.

Catalog migration **v7** adds a `roll` table: identifier, film stock, camera
body, lens, EI shot at, push/pull in stops, developer and development notes,
lab, and scan date. `CatalogEntry` gains a nullable `rollID` and a frame
number.

The library sidebar groups by roll. The filmstrip already draws a film rebate
with edge-printed frame numbers and stock names — Phase 3 is what makes that
printing true instead of decorative.

### Roll-wide conversion sync

Sample the base and the black point on one frame, apply the whole conversion
to every frame in the roll.

The film base is a property of the roll and the scanner, not of the frame.
Every tool that makes you sample it 36 times is wasting 35 samples. This is
the workflow feature that matters most and it is a direct consequence of
having a roll model at all.

Applied as one undoable action across the roll, skipping frames whose base was
individually sampled.

### Frame detection

Find the image rectangle inside the film rebate: locate the dense image area
against the clear border, return a crop and a straighten angle. The user
reviews it — it writes to `Geometry`, which is non-destructive and undoable
like any other edit.

When a scan holds several frames, split it into separate catalog entries
sharing the original file, which is what the virtual-copy mechanism already
does.

Detection also hands `Dmin` a rebate sample, which is the most reliable base
measurement available: actual unexposed film, not the brightest thing in the
picture.

### Emulsion flip

Negatives scanned emulsion-side up are laterally reversed. `Geometry` already
has `flipHorizontal`; this is one roll-wide action that sets it, because the
mistake is made per roll and not per frame.

### Dust and scratch removal

No infrared channel on a DSLR scan, so detection is morphological: local
extrema that diverge from a median-filtered version beyond a threshold,
bounded above and below in size so that stars, specular highlights and fine
detail are not candidates. Detected spots are inpainted through the existing
`PatchMatchInpainter`.

Off by default. Amount and size controls, and an overlay that shows what it is
about to touch before it touches it — the failure mode here is eating real
detail, and the defence is making the user able to see it.

Runs inside the memoised developed-source prefix alongside retouch, so
dragging a tone slider does not re-run detection.

### Contact sheet

Export a roll as a contact sheet: frames in order, frame numbers, roll
metadata in the margin.

### Files

`Sources/Film/Roll.swift`, `Sources/Film/FrameDetector.swift`,
`Sources/Film/DustDetector.swift`, `Sources/Pipeline/DustRenderer.swift`,
`Sources/Views/RollModel.swift`, `Sources/Views/SliderPanel/ScanPanel.swift`.

`EditorModel` is already 1080 lines. Roll and scan actions go into a separate
`RollModel` rather than growing it further.

## Phase 4 — The library

The develop side is close to Lightroom. The library side is a sidebar list,
and a sidebar list is not how anyone culls 476 files.

### Grid

A real grid browser as a first-class view alongside the loupe, with thumbnail
size, sort order, and the existing rating / flag / colour-label filters acting
on the visible set. `G` for grid, `E` for loupe, matching the muscle memory
every photographer already has. Multi-select with shift and command.

The catalog already stores everything this needs; there is simply no view that
shows more than one photo at a time.

### Collections

Named, ordered sets of entries that are independent of where the files sit on
disk, plus smart collections defined by the filters that already exist. A
migration adds a `collection` table and a join.

Rolls (Phase 3) are a different thing and stay a different thing: a roll is a
physical fact about a strip of film, a collection is an editorial choice.

### Keywords

A keyword table, a join, a token field in the inspector, and keyword as a
search term. Written to the catalog only — the originals stay untouched, which
is the same promise the rest of the app makes.

### Sync across a selection

Copy/paste develop settings exists but moves one photo at a time. This adds
paste-to-selection and a sync sheet that chooses which groups of settings
travel, as one undoable action across every selected entry.

Phase 3's roll-wide conversion sync is the specialised case of this; the
general case belongs here, and the two share an implementation.

### Files

`Sources/Views/GridView.swift`, `Sources/Views/CollectionSidebar.swift`,
`Sources/Models/Collection.swift`, `Sources/Models/Keyword.swift`,
`Sources/Views/SyncSettingsSheet.swift`.

## Risks

**Changing conversion math silently alters every existing negative.** Handled
by freezing the matrix model permanently and making the switch an explicit,
snapshotted, undoable action.

**Dust detection eats real detail.** Handled by size bounds, an overlay that
previews the detection, and defaulting to off.

**Frame detection fails on a low-contrast rebate.** It writes to `Geometry`,
so a wrong answer is a crop the user adjusts, never a destroyed file.

**The density model is only as good as its inputs.** A scan with no rebate
visible gives no reliable `Dmin`. Auto-invert falls back to a percentile
estimate and the panel says which one it used, the way the current panel
already distinguishes "sampled from this scan" from "assumed default".

## Sequencing

Phase 1 first: it is the safety net every later phase lands on. Phase 2 before
3, because frame detection feeds the base sample into the converter and not
the other way around. Phase 4 could be built at any point — it touches none of
the film work — and is placed fourth because a better library makes a bigger
difference once there is something worth browsing. Phase 5 last.

Each phase gets its own spec, its own implementation plan, and ends green.
